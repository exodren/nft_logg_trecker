## Сценарий обработки (§1, §2.3, §7, §8, §10, §13, §20)

```
MTProto Scanner → Parser → DB: gifts + listings            ← сохраняется ВСЕГДА
  → Этап 1: фильтр по листингу (коллекция, цена, атрибуты)  [F.1]
      ├─ 0 подходящих пользователей → owner_lookup_status = NOT_NEEDED, конец (запроса нет)
      └─ ≥1 пользователь → processing_queue (owner_lookup, высокий приоритет)
  → Кэш владельца актуален? ── да → данные из кэша (запроса нет)            [K4.8]
      └─ нет → бюджет/квота позволяют? ── нет → DEFERRED, листинг остаётся  [K4.7, F.4]
              └─ да → KartoshkaApiProvider: GET /v1/gift/{ref}               [K4.3]
  → DB: owners, owner_lookup_cache, api_usage
  → Этап 2: фильтр по владельцу для каждого пользователя из этапа 1        [F.2]
  → Notification Service → Telegram Bot                                      [T6]

Новый или изменённый фильтр пользователя → backfill [F.3]:
  сохранённые активные листинги → этап 1 только для этого фильтра → та же очередь
  (низкий приоритет) → кэш → бюджет → этап 2 → результат в боте
```
Листинг сохраняется до любой фильтрации и обращения к API (§13, §20 п. 1).

## Двухэтапная фильтрация owner lookup (§20, окончательное решение 2026-11-10)

### F.1 Этап 1 — фильтр по листингу — DONE (`app/services/filters.py`, `pipeline.py`)
- **Описание:** `app/services/filters.py`. Для каждого сохранённого нового листинга проверить активные фильтры пользователей с включёнными уведомлениями только по характеристикам листинга: коллекция, диапазон цены, атрибуты (модель, фон, паттерн), остальные характеристики. Критерии владельца на этом этапе не проверяются. Результат — список подходящих пользователей. Если он пуст: `owner_lookup_status = NOT_NEEDED`, запроса нет. Иначе — задача `owner_lookup` в очередь. Фильтр без критериев листинга подходит под любой листинг (это осознанно: такие пользователи увеличивают число запросов, их сдерживает бюджет K4.7).
- **Зависимости:** T1.4, T3.4.
- **Результат:** функция предфильтра, чистая, без сети.
- **Готово, когда:** решение принимается только по данным листинга и `user_filters`; листинг сохранён до вызова.
- **Тесты:** 0 подходящих → нет задачи; ≥1 → одна задача; каждый критерий отдельно; фильтр без критериев листинга; критерии владельца игнорируются.

### F.2 Этап 2 — фильтр по владельцу — DONE (матрица 5×2 в тестах)
- **Описание:** после получения данных владельца (из кэша или API) для каждого пользователя из этапа 1 проверить критерии владельца: наличие username, наличие Telegram ID, другие критерии, зависящие от владельца. Правила (§20 п. 6 — без ложных совпадений):
  - пользователь **без** критериев владельца получает листинг при любом статусе; карточка показывает фактический статус (`FOUND`, `HIDDEN`, «данные владельца недоступны»);
  - пользователь **с** критериями владельца получает листинг только при `FOUND` и выполнении всех критериев;
  - `HIDDEN`, `NOT_FOUND` — окончательный результат: критерии владельца не выполнены;
  - `UNAVAILABLE`, `ERROR`, `DEFERRED` — данных нет: критерии владельца не выполнены сейчас, листинг ждёт повторной обработки (F.4).
- **Зависимости:** F.1, K4.4.
- **Результат:** функция отбора получателей, чистая, без сети.
- **Готово, когда:** ни при каком статусе кроме `FOUND` пользователь с критериями владельца не получает совпадение.
- **Тесты:** матрица «статус × наличие критериев владельца» (5 × 2), username есть/нет, Telegram ID есть/нет.

### F.3 Повторная обработка при новом фильтре (backfill) — DONE (`Pipeline.backfill`; запуск из /settings — T5.5)
- **Описание:** при создании или изменении фильтра пользователем — проверить ранее сохранённые **активные** листинги по этапу 1 только для этого фильтра, совпавшие поставить в очередь с низким приоритетом. Далее обычный путь: кэш → бюджет → API → этап 2. Запросы учитывают кэш (K4.8) и бюджет (K4.7); новые листинги имеют приоритет. Повторная задача по тому же NFT не создаётся (дедупликация T3.5). Результат показывается пользователю в боте списком подходящих листингов, массовой рассылки уведомлений по старым листингам нет.
- **Зависимости:** F.1, F.2, T3.5, K4.7, K4.8, T5.5.
- **Результат:** сервис backfill, запускаемый из `/settings`.
- **Готово, когда:** новый фильтр находит подходящие сохранённые листинги; NFT с актуальным кэшем не вызывают запрос; при исчерпании бюджета backfill останавливается, не затрагивая обработку новых листингов.
- **Тесты:** backfill с кэшем → 0 запросов; без кэша → по одному запросу на NFT; исчерпание бюджета посреди backfill; приоритет новых листингов; повторное сохранение того же фильтра не дублирует задачи.

### F.4 Отложенная обработка — DONE (defer до 00:00 UTC или +15 мин, `wake_deferred`)
- **Описание:** если бюджет или квота исчерпаны или API недоступен (402, 429 после повторов, 5xx, сеть), листинг остаётся в БД со статусом `DEFERRED` (или `FAILED` после лимита повторов). После восстановления (сброс квоты в 00:00 UTC, пополнение баланса, доступность API) отложенные листинги, которые ещё активны, обрабатываются повторно через тот же путь: кэш → бюджет → API → этап 2.
- **Зависимости:** K4.5, K4.7, T3.5.
- **Результат:** логика возврата отложенных задач.
- **Готово, когда:** бюджет исчерпан → листинг в БД, запроса нет; после восстановления — один запрос и обычная фильтрация.
- **Тесты:** исчерпание бюджета, 402, недоступность API, восстановление, неактивный листинг не обрабатывается повторно.

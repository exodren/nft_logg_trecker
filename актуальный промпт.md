# 1. КОНТЕКСТ ПРОЕКТА

Мы разрабатываем Telegram-бота для отслеживания Telegram NFT Gifts.

Основная задача приложения:

1. Обнаруживать новые NFT-листинги через Telegram MTProto.
2. Определять коллекцию и номер подарка.
3. Получать актуальную информацию о подарке и его владельце через официальный API kartoshka.free.
4. Извлекать доступные Telegram ID и username владельца.
5. Сохранять полученные сведения в собственной базе данных.
6. Отправлять уведомления пользователям Telegram-бота.
7. Предоставлять пользователям поиск, фильтры и просмотр найденных NFT.

**Ключевая бизнес-логика:**

MTProto отвечает за обнаружение новых листингов.

Официальный API kartoshka.free отвечает за получение дополнительной информации о подарке и владельце.

Наш Telegram-бот отвечает за взаимодействие с пользователями и доставку уведомлений.

Эти компоненты должны быть независимыми и взаимодействовать через чёткие интерфейсы.

# 2. ПРИНЦИПИАЛЬНОЕ ИЗМЕНЕНИЕ ИСТОЧНИКА ДАННЫХ

## 2.1. Полная замена See.TG Resolver

Ранее в архитектуре использовался See.TG Resolver.

Теперь он полностью заменяется на:

**Kartoshka API Provider.**

Официальная документация:

https://kartoshka.free/

Правила API:

https://kartoshka.free/rules.js

Проверка тарифов:

`GET /v1/pricing`

Kartoshka API является официальным способом интеграции с данными See.TG через приложение kartoshka.free.

Мы используем предоставленный API, а не внутренний GraphQL API сайта.

Не возвращайся к старой реализации See.TG GraphQL.

Не используй DevTools для воспроизведения внутренних запросов сайта.

Не создавай альтернативный парсер внутреннего API See.TG.

Не предлагай возвращаться к исследованию See.TG.

## 2.2. Правила работы с Kartoshka API

Используй только официально документированные возможности kartoshka.free.

Не придумывай endpoint, параметры, поля JSON или форматы ответов.

Если документация не описывает конкретное поле, не предполагай его существование.

Если документация неполная, используй реальные ответы API для уточнения структуры.

Не трать время на повторное исследование уже установленных фактов.

Условия использования API должны соблюдаться. Мы оплачиваем запросы с баланса сервиса и используем предоставленный официальный механизм доступа.

Не пытайся обходить приватность владельцев.

Не используй методы поиска скрытых владельцев `/who` и `/owners/search` в основном MVP.

Не пытайся получать информацию, которую владелец скрыл настройками приватности.

Не добавляй повторные согласования с See.TG в план разработки: источник интеграции уже выбран.

## 2.3. Основной endpoint

Основной метод получения данных:

`GET /v1/gift/{ref}`

Где `ref` формируется в соответствии с официальной документацией.

Предполагаемый формат идентификатора подарка:

`CollectionName-Number`

Например:

`IonGem-3185`

Однако перед реализацией проверь точный формат в документации.

Основной сценарий:

1. MTProto обнаруживает новый листинг.
2. Parser извлекает коллекцию и номер.
3. Формируется ref.
4. Kartoshka API Provider выполняет запрос.
5. Получает доступные данные о подарке и владельце.
6. Нормализует ответ.
7. Сохраняет данные.
8. Передаёт событие Notification Service.

Не выполняй отдельный запрос `/v1/owner/{ref}`, если необходимые сведения уже присутствуют в ответе `/v1/gift/{ref}`.

Дополнительные endpoints можно предусмотреть в архитектуре, но не подключать без конкретной необходимости.

## 2.4. Стоимость API

Предварительно известные тарифы:

- 100 бесплатных запросов в сутки.
- Обычный успешный запрос: 0.00005 TON.
- Дополнительные методы могут иметь другую стоимость.

Это предварительные значения. Перед реализацией механизма учёта расходов сверь их с актуальным `/v1/pricing`.

Не зашивай тарифы в бизнес-логику.

Создай отдельный механизм получения и учёта стоимости запросов.

Ожидаемая нагрузка:

- Минимум: 3 000 запросов в сутки.
- Среднее: 5 000 запросов в сутки.
- Максимум: 7 000 запросов в сутки.

Архитектура должна выдерживать эту нагрузку без лишних запросов и повторной оплаты уже обработанных NFT.

# 20. АРХИТЕКТУРНОЕ РЕШЕНИЕ: ДВУХЭТАПНАЯ ФИЛЬТРАЦИЯ OWNER LOOKUP (2026-11-10)

Окончательное решение владельца проекта. Уточняет §8 K4.3 («для каждого нового NFT») и §10: запрос владельца выполняется не для каждого NFT, а только после предварительной фильтрации. Не возвращаться к варианту запроса для каждого NFT.

1. Каждый листинг сохраняется в БД независимо от результатов фильтрации и API.
2. **Этап 1 — до Kartoshka API:** фильтры по характеристикам листинга (коллекция, цена, атрибуты и остальные характеристики). Если листинг не подходит ни одному пользователю, платный запрос владельца не выполняется.
3. **Этап 2 — после Kartoshka API:** фильтры по владельцу (наличие username, наличие Telegram ID и другие критерии, зависящие от владельца).
4. Если данные владельца есть в актуальном кэше, повторный запрос не выполняется.
5. Если API недоступен или бюджет исчерпан, базовый листинг остаётся в БД.
6. Пользователи с фильтрами по владельцу не получают совпадений при отсутствии данных владельца.
7. При создании пользователем нового фильтра ранее сохранённые листинги можно обработать повторно; повторные запросы учитывают кэш и бюджет.

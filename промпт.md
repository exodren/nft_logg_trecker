# 4. LISTING SCANNER — ОСНОВНОЙ ДВИЖОК

Это один из самых важных компонентов проекта.

Главная задача Scanner — обнаруживать новые выставления NFT.

Необходимо отличать:

- совершенно новый NFT;
- новый листинг уже существующего NFT;
- повторно полученный листинг;
- изменение цены существующего листинга;
- снятие NFT с продажи;
- NFT, который больше не присутствует в выдаче.

## 4.1 Получение данных

Используй существующий рабочий механизм payments.getResaleStarGifts.

Scanner должен:

1. Получать первую страницу resale listings.
2. Обрабатывать полученные NFT.
3. Получать следующие страницы, если это необходимо.
4. Корректно работать с offset и пагинацией.
5. Не терять записи между страницами.
6. Не создавать повторные записи.
7. Запоминать состояние последнего успешного сканирования.

Не запускай чрезмерно частые запросы.

Частота сканирования должна быть конфигурируемой.

Не нарушай ограничения Telegram.

## 4.2 Что извлекать из каждого NFT

Сохраняй все доступные значимые поля:

Идентификация:

- id;
- gift_id;
- title;
- slug;
- num.

Характеристики:

- model;
- model rarity;
- backdrop;
- backdrop rarity;
- pattern;
- pattern rarity.

Состояние:

- burned;
- crafted;
- minted;
- availability_issued;
- availability_total.

Владелец и адреса:

- owner_id;
- owner_name;
- owner_address;
- gift_address;
- host_id.

Продажа:

- resell_amount;
- StarsAmount;
- StarsTonAmount;
- value_amount;
- value_currency;
- onSale, если присутствует.

Дополнительно:

- raw MTProto object;
- время обнаружения;
- время последнего обновления;
- источник данных.

Не удаляй исходные данные после парсинга.

## 4.3 Обнаружение новых листингов

Создай механизм определения новых листингов.

Идентификатор NFT должен быть отделён от идентификатора конкретного листинга.

Один NFT может выставляться повторно.

Нужно различать:

NFT:
collection + number

и

Listing:
конкретное состояние выставления NFT.

Если в MTProto имеются подходящие стабильные идентификаторы листинга, используй их после проверки.

Не считай одну только цену идентификатором листинга.

Если стабильного ID нет, разработай составной ключ на основе подтверждённых полей и задокументируй его ограничения.

## 4.4 Изменение цены

Если уже известный NFT появился снова с другой ценой:

- не создавай новый NFT;
- сохраняй изменение;
- записывай старую цену;
- записывай новую цену;
- фиксируй время изменения.

Уведомления об изменении цены пока должны быть опциональными.

Основной MVP — новые листинги.

## 4.5 Исчезновение листинга

Если NFT исчез из актуальной выдачи:

- не удаляй его из базы;
- сохраняй последнюю известную цену;
- отмечай состояние как inactive или unknown;
- не утверждай, что NFT продан, если продажа не подтверждена.

# 6. PROCESSING QUEUE

Создай очередь обработки новых листингов.

Scanner не должен ожидать завершения всех внешних операций.

После обнаружения нового листинга:

1. Нормализовать NFT.
2. Сохранить первичную запись.
3. Создать задачу на обогащение.
4. Передать её в очередь.

Queue должна поддерживать:

- добавление задач;
- ограниченное количество параллельных workers;
- повторные попытки;
- exponential backoff;
- обработку ошибок;
- дедупликацию;
- восстановление незавершённых задач после перезапуска.

Предусмотри состояния:

- pending;
- processing;
- completed;
- retry;
- failed.

Задача не должна теряться при аварийном завершении процесса.

Для первоначального MVP допустимо использовать очередь на базе БД и asyncio.

Не подключай Redis или RabbitMQ без реальной необходимости.

# 7. SEE.TG RESOLVER

## Owner Data Provider — Official kartoshka.free API

### 1. Основной источник данных

Для получения информации о владельцах Telegram NFT Gifts необходимо использовать **официальный публичный API kartoshka.free**.

Официальная документация:
- https://kartoshka.free/

Использовать исключительно документированные API endpoints, параметры запросов, схемы ответов, правила аутентификации и ограничения, описанные в официальной документации.

Не использовать внутренний GraphQL API See.TG и не воспроизводить запросы сайта See.TG.

### 2. Основной сценарий работы

После обнаружения нового NFT через MTProto Scanner:

1. Извлечь коллекцию NFT.
2. Извлечь номер подарка.
3. Сформировать идентификатор подарка в формате, предусмотренном API.
4. Выполнить запрос к официальному endpoint получения информации о подарке:
   `GET /v1/gift/{ref}`
5. Получить доступные сведения о подарке и его владельце.
6. Если API возвращает Telegram ID и username — сохранить их в базе данных.
7. Сохранить статус доступности владельца и остальные полезные сведения.
8. Передать результат Notification Service для отправки уведомления пользователю.

Один запрос `/v1/gift/{ref}` должен быть основным способом получения информации о подарке и его текущем владельце. Не выполнять отдельный запрос владельца без необходимости.

### 3. Обработка данных владельца

Необходимо предусмотреть следующие состояния:

- `FOUND` — владелец найден, доступен Telegram ID и/или username.
- `HIDDEN` — владелец скрыт настройками приватности.
- `NOT_FOUND` — владелец не найден в ответе API.
- `UNAVAILABLE` — данные временно недоступны.
- `ERROR` — ошибка запроса или обработки ответа.

Не путать отсутствие username с отсутствием владельца.

Если username отсутствует, но Telegram ID присутствует, сохранить Telegram ID.

Если владелец скрыт, не пытаться обходить настройки приватности. Сохранить соответствующий статус.

### 4. Дополнительные endpoints

Изучить официальную документацию и предусмотреть возможность подключения дополнительных методов:

- `GET /v1/owner/{ref}` — получение информации о владельце.
- `GET /v1/gift/{ref}/history` — история подарка.
- `GET /v1/gift/{ref}/who` — дополнительный поиск владельца.
- `GET /v1/owners/search` — поиск владельцев.

Не использовать дополнительные платные endpoints автоматически в основном сценарии. Они должны подключаться только при наличии конкретной бизнес-необходимости и отдельного разрешения в конфигурации.

Историю предыдущих владельцев пока не реализовывать в основном MVP.

### 5. Стоимость и контроль расходов

По опубликованному тарифу:

- Бесплатная квота: 100 запросов в сутки.
- Обычный успешный запрос: 0.00005 TON.
- Дополнительные методы поиска владельцев могут стоить существенно дороже.

Не зашивать стоимость и лимиты непосредственно в код. Вынести тарифные параметры в конфигурацию, чтобы их можно было обновлять без изменения бизнес-логики.

Реализовать:

- Подсчёт запросов за сутки.
- Подсчёт успешных и неуспешных запросов.
- Учёт бесплатной квоты.
- Расчёт приблизительных расходов в TON.
- Настраиваемый дневной лимит расходов.
- Предупреждение администратора при приближении к лимиту.
- Возможность отключить новые API-запросы при достижении установленного бюджета.

Не считать HTTP 2xx гарантией наличия информации о владельце: проверять фактическую структуру и содержимое ответа.

### 6. Производительность и надёжность

Поскольку ожидаемая нагрузка составляет примерно 3 000–7 000 запросов в сутки, необходимо предусмотреть:

- Асинхронные HTTP-запросы.
- Ограничение параллельных запросов.
- Очередь обработки NFT.
- Соблюдение опубликованных API rate limits.
- Retry с exponential backoff для временных ошибок.
- Обработку HTTP 429 и Retry-After.
- Таймауты запросов.
- Кэширование результатов.
- Защиту от повторной оплаты уже обработанных NFT.
- Логирование запросов и ошибок без раскрытия секретных ключей.

Не отправлять повторный запрос для NFT, если актуальный результат уже сохранён и срок его актуальности не истёк.

### 7. Архитектура интеграции

Реализовать отдельный модуль `KartoshkaApiProvider`.

Он должен быть независим от MTProto Scanner, Telegram Bot и Notification Service.

Предусмотреть интерфейс провайдера данных о владельце, чтобы в будущем можно было подключать другие разрешённые источники без изменения основной логики приложения.

API-ключи и другие секреты хранить в `.env`. Не размещать их в исходном коде, логах или Git.

# 19. КРИТЕРИИ ГОТОВНОСТИ MVP

MVP не считается готовым, если просто запускается Telegram Bot.

1. MTProto подключается.

3. Parser извлекает данные NFT.
4. Database сохраняет NFT.
5. Scanner обнаруживает новый листинг.
6. Deduplication исключает повтор.
7. Listing попадает в очередь.
8. Worker обрабатывает задачу.
9. Owner Resolver возвращает корректный статус.
10. Notification Service выбирает подходящих пользователей.
11. Telegram Bot отправляет карточку.
12. Повторный запуск не создаёт дубликаты.
13. /search находит сохранённый NFT.
14. /stats показывает актуальную статистику.
15. Настройки пользователя сохраняются после перезапуска.

Если Owner Provider ещё не подключён, тест должен успешно проходить с MockProvider и явно обозначенным статусом permission_required или provider_unavailable.

Не подменяй тестовые данные реальными.

После редактирования:
- запусти соответствующие тесты;
- проверь импорты;
- проверь синтаксис;
- проверь, что существующие модули продолжают работать.

Если тест не проходит, исправь причину, а не отключай тест.

Если зависимость отсутствует, сначала проверь текущую среду и зависимости проекта.

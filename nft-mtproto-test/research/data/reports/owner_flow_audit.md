# Аудит потока NFT → Owner Lookup → Notifications

Дата: 2026-11-10. Проверен реальный поток вызовов, не только имена функций.

## Поток (как реализовано)

```
ListingScanner.scan_type → parse_page → listings.ingest (gifts + listings, всегда)
  → Pipeline.on_events (та же транзакция): stage1(filter, listing) по всем активным фильтрам
      нет совпадений → owner_lookup_status = NOT_NEEDED, запроса нет
      есть → enqueue("owner:{gift_id}")
  → Pipeline.handle → OwnerResolver.resolve(gift_id) → cache.get_fresh → usage.can_spend
      → provider.lookup(gift.slug)            ← единственный вызов Kartoshka, аргумент — slug NFT
  → cache.store → stage2(filter, owner) → add_notification → NotificationSender
```

## Проверки

| Вопрос | Результат |
|---|---|
| username или Telegram ID как критерий поиска NFT | **Нет.** Единственный вызов провайдера — `lookup(gift.slug)` (`enrichment.py`). `/v1/owner/*`, `/who`, `/owners/search` не реализованы. Поиск в боте (`queries.search`) — по коллекции и номеру в локальной БД. |
| Фильтры владельца влияют на обнаружение NFT | **Нет.** Сканер не читает фильтры. `stage1` не смотрит на критерии владельца (тест `test_owner_values_never_affect_stage_a`). |
| Получение владельца как отдельный поиск по пользователю | **Нет.** |
| Пустой фильтр | Однозначно, но дорого: фильтр без критериев NFT подходит под любой листинг на этапе A. Новые пользователи создаются с выключенными уведомлениями, поэтому пустой фильтр не участвует, пока пользователь сам не включит уведомления. См. «Открытый вопрос». |
| Повторная отправка NFT в Kartoshka | Кэш по NFT (`API_CACHE_TTL`), одна активная задача на NFT, backfill пропускает закэшированные. Найдены и исправлены 2 случая (ниже). |

## Найдено и исправлено

1. **Не было проверки конкретного владельца.** Этап B проверял только «есть username» / «есть Telegram ID». Добавлены `user_filters.owner_usernames` и `owner_telegram_ids` (миграция `adb2e9310ff6`), команда `/filter owner @username, 8556771897`. Сравнение — с владельцем каждого найденного NFT: username без `@` и без учёта регистра, ID — точно. Отсутствие username, HIDDEN, NOT_FOUND, UNAVAILABLE, ERROR — не совпадение.
2. **Устаревший владелец после перепродажи.** Новый эпизод из-за смены продавца брал владельца из кэша (до 24 ч) — пользователю ушёл бы прежний владелец. Теперь смена продавца сбрасывает кэш NFT (`cache.invalidate`), и владелец запрашивается заново. Повторное выставление тем же продавцом по-прежнему берётся из кэша.
3. **Повторная оплата неразобранного ответа.** Оплаченный 2xx, который не удалось разобрать (`ERROR`), не кэшировался и покупался снова при каждом появлении NFT. Теперь он кэшируется на 1 ч (`PAID_ERROR_TTL_S`). Неоплаченные ошибки (429, 5xx, сеть, 402) повторяются, как раньше.

## Правило «владелец только с username» (уточнение 2026-11-10)

- `apply_owner_rules` (`app/providers/base.py`): FOUND без username → `NO_USERNAME`, Telegram ID отбрасывается. Применяется в `OwnerResolver` и в `cache.store`.
- `owners`: запись только для FOUND с username (ID — дополнительно). `NO_USERNAME`, `HIDDEN`, `NOT_FOUND` — только строка в `owner_lookup_cache` с TTL: повторной оплаты за NFT нет (тест на все 4 случая).
- Этап B: любое условие на владельца требует username; ID без username не совпадает ни с одним условием, в том числе `require_telegram_id` и конкретным ID.
- Карточка: блок владельца (`@username`, ID) только при username; остальные — без блока владельца. Скрытый владелец в Telegram не упоминается (решение владельца проекта): строка «🔒 Владелец скрыл профиль» пишется в лог (`app.api` при запросе, `app.bot` при отправке уведомления). Лог — `logs/app.log`, ротация каждые 6 ч, 28 файлов. Строка «Данные о владельце: see.tg» — только когда эти данные показаны.
- `/stats`: «с username», «без username», «скрытых».
- Схема БД не менялась (статус — строка), миграция не нужна; `alembic check` чистый.
- `pytest` — 188 passed.

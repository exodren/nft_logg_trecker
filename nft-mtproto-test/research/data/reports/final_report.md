# Telegram Gifts: идентификация продавцов NFT — итоговый отчёт

Дата прогона: 2026-11-08. Одна авторизованная сессия, только чтение. Запросов к Telegram в основном прогоне: порядка 100, FloodWait: 0.
Исходные ответы: `data/raw/`, агрегаты: `data/parsed/`, вердикты: `hypotheses.json`.

## Ответ на главный вопрос

> Можно ли через официальный Marketplace API обнаруживать листинги, извлекать числовой ID продавца и разрешать его в username?

| Шаг | Результат |
|---|---|
| Обнаруживать активные листинги | **Да** |
| Извлечь числовой Telegram ID продавца из листинга | **Нет**: `owner_id = null` в 2250 из 2250 листингов |
| Разрешить ID в username | **Неприменимо**: ID нет. Отдельно: голый ID без `access_hash` не резолвится (1 проверка, ответ пустой) |
| Получить username косвенно | **Частично**: `@x` внутри `owner_name` есть у 396 из 2250 (17,6%) |

Ограничение вывода: все данные получены с точки зрения одного аккаунта. Сравнения с интерфейсом Telegram не было.

## B. Главный результат

`getResaleStarGifts` стабильно отдаёт листинги, но не личность продавца. По 2250 листингам:

| Поле | Заполнено | Практический смысл |
|---|---:|---|
| `slug`, `num`, `id`, `gift_id`, `attributes` | 100% | Идентификация NFT |
| `resell_amount` | 100% | Цена, два значения (XTR и TON) |
| `owner_name` | 100% | **Только отображаемое имя**, задаётся пользователем |
| `gift_address` | 25,6% | Адрес контракта NFT, если он on-chain. **Не кошелёк** |
| `released_by` | 13,3% | `PeerChannel` выпустившего бренда. **Не продавец** |
| `owner_id`, `host_id`, `owner_address` | 0% | В листингах не приходят |

Ловушка: `result.users` непуст и содержит username, но это не продавцы. Из 510 сущностей: 288 — получатели и 208 — отправители исходного подарка, 6 — `released_by`, 8 не объяснены. Имя получателя расходится с `owner_name` примерно в 97% случаев, поэтому считать его продавцом нельзя.

## C. Username

- `owner_id` не приходит, поэтому разрешать нечего.
- `resolve_telegram_user` реализована и покрыта тестами, но на реальных данных вернула `no_peer` для всех листингов.
- `users.getUsers` с `access_hash = 0` вернул пустой результат. Числовой ID сам по себе аккаунт не адресует (1 проверка).
- Рабочий косвенный путь: взять `@x` из `owner_name`, вызвать `contacts.resolveUsername`, опубликовать только при точном совпадении имени аккаунта с `owner_name`. Покрывает около 17,6% листингов. Выборка из 5 мала, это предварительный результат.

## D. Owner, seller, host

- **`owner_name`** — имя, не username и не ID.
- **`owner_id`** — не наблюдался ни разу. Равенство seller не проверено и не должно предполагаться.
- **`host_id`** — не наблюдался, вывод невозможен.
- **`owner_address`** — поправка к гипотезе C: поле может содержать TON DNS-домен вида `username.t.me`, а не адрес кошелька. Значит, его нельзя слепо считать кошельком.
- **`gift_address`** — контракт NFT, отличается от `owner_address` (проверено на Snoop Cigar).

`normalize_event` хранит эти сущности раздельно и оставляет seller `unknown`, пока нет доказательства.

## F. Обнаружение

**Листинги.**
- Единого метода нет: `gift_id` обязателен, нужен обход по типам. В каталоге 151 тип, 124 с листингами, всего 826 915 листингов.
- Лимит страницы 100 (значение 101 молча обрезается). Пагинация стабильна: 300 из 300 уникальны на 6 страницах.
- Полный обход: минимум 8 270 запросов, примерно 3,4 часа при 1,5 с на запрос. Для реального времени не годится.
- Опрос первой страницы всех типов: 124 запроса, около 3 минут на цикл.
- За 90 с на первой странице появилось 5 новых позиций (места 0, 2, 3, 5, 9). Порядок по умолчанию похож на «свежие сверху», но не доказан.
- `count` не изменился при появлении новых позиций, поэтому он не индикатор новых листингов.
- Мусорный `offset` даёт 0 записей и **непустой** `next_offset`: без защиты возможен вечный цикл.
- Несуществующий `gift_id`: `STARGIFT_INVALID`. Тип без листингов: `count = 0`.

**Изменения цены.** Между листингом и карточкой цена различалась у 14 из 25. В 6 просмотренных случаях менялась только сконвертированная валюта. Сравнивать нужно цену в валюте продавца: `price_key`.

**Снятие и продажа.** Отсутствие на частичном скане ничего не значит. Адресная проверка известного slug через `getUniqueStarGift` показывает, что `resell_amount` пропал. Различить продажу и снятие этим способом нельзя; смена `owner_name` — только косвенный признак.

**Минт.** `availability_issued` совпадает с максимальным существующим номером: `Title-N` существует, `N+1` и `N+2` нет (3 из 3 типов). Возможный путь: опрос `availability_issued` и проверка следующих slug. За 60 с значение на 3 типах не изменилось, так что **обнаружение реального минта не наблюдалось**. Минт не связан с листингом: новый NFT может не появиться в продаже.

**Предыдущий владелец.** `unknown`. Метода истории нет. `UniqueStarGiftValueInfo` даёт только `last_sale_date` и цены. On-chain история (`parse_history.py`) работает лишь для выведенных NFT и даёт кошельки, а не аккаунты. По схеме сервисные сообщения доступны только в диалогах самого аккаунта (не тестировалось).

## G. Ограничения

- В проверенных листингах Telegram не отдаёт ID владельца, а у владельца без `@` в имени username из них получить нельзя.
- Идентификация невозможна, если имя не содержит `@` и NFT не выведен on-chain с привязанным доменом.
- Не проверено: сравнение с UI, другой аккаунт-наблюдатель, длительный опрос, порядок сортировки, различие продажи и снятия, Kurigram вживую.
- Выборка: 15 из 124 типов, до 3 страниц на тип.
- Прежний вывод об обходе профилей через `getSavedStarGifts` (заметки проекта) здесь **не тестировался и не реализован**: массовый опрос чужих профилей нарушает правило задания, а скрытие подарков — выбор самого владельца.

## Ограничение: сопоставление NFT с профилями

Telegram не предоставляет в листингах данных, достаточных для связи NFT с аккаунтом: `owner_id` пуст в 2250 из 2250. Оставшиеся пути требуют массовых запросов по аккаунтам и поэтому не выполняются:

| Действие | Решение | Причина и альтернатива |
|---|---|---|
| `getResaleStarGifts`, `getUniqueStarGift`, `getUniqueStarGiftValueInfo`, `getStarGifts` | Выполнять | Данные о NFT и рынке |
| История событий по `slug` | Выполнять | Публичные события NFT |
| `owner_name` как текст карточки | Выполнять | Без сопоставления с аккаунтом |
| On-chain история на уровне кошельков | Выполнять | Без привязки кошелька к аккаунту |
| `resolveUsername` для `@x` из `owner_name` | Не выполнять | При 17,6% от 826 915 листингов это около 145 000 запросов. Альтернатива: продавец подключается сам |
| `getSavedStarGifts` по чужим профилям | Не выполнять | Массовый перебор пользователей. Допустимо для своего аккаунта и подключившихся продавцов |
| `gram.org` по каждому адресу | Не выполнять | То же сопоставление через кошелёк |
| `getFullUser` (рейтинг, статус, цена сообщений) | Не выполнять | Только для подключившихся продавцов |
| `result.users` | Только в сырых данных | Участники исходного дарения, не продавцы |
| `sendStarGiftOffer` | Не выполнять без согласования | Запись, вне read-only allowlist |

## H. Рекомендации

1. **Поток листингов:** опрос первой страницы `getResaleStarGifts` по 124 типам на Telethon; Portals как кандидат на дополнительный поток.
2. **Личность:** хранить `owner_name` только как текст карточки, без сопоставления с аккаунтом. Прежняя рекомендация проверять `@x` через `resolveUsername` отозвана, см. «Ограничение: сопоставление NFT с профилями».
3. **On-chain:** `owner_address` хранить как текст карточки. Массовое сопоставление доменов `.t.me` с аккаунтами не выполнять.
4. **База данных:** раздельные поля owner, seller, host, wallet, contract; seller = `unknown` по умолчанию.
5. Заложить в продукт, что большинство листингов (около 82%) останется без username.
